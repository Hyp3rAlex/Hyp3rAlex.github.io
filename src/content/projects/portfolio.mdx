## Summary

I wanted a portfolio that a hiring engineer could check. Each case study on this site was written from an audit of the actual repository: what the code does, which numbers can be traced to a file or a fresh test run, and what must not be claimed. Where a project was team work, the page says which part is mine.

The site itself is a small engineering project. It is static HTML generated by Astro, styled with hand-written CSS, and enhanced by a few kilobytes of first-party TypeScript. The interactive demos are clean re-implementations of each project's core logic, unit-tested against values exported from the original code, and they run entirely in the browser.

There is no backend, no analytics, no cookie and no request to any third party. Hosting is GitHub Pages; the cost is zero.

## Architecture

- **Content.** Case studies are MDX files in a typed content collection. The schema requires a role statement, an audited revision and date, and two to four facts; a build with a malformed entry fails.
- **Facts in one place.** Name, degrees, experience and links live in a single typed module. Home, About, Recruiter, Résumé, the command palette and the structured data all read from it.
- **Rendering.** Every page is generated at build time. Card visuals and architecture diagrams are inline SVG or HTML computed from project data during the build, so they follow the theme and need no JavaScript.
- **Interaction.** Demos, the command palette, the project filter and the recruiter focus selector are custom elements written in plain TypeScript. Each server-renders a useful default, so the page works with JavaScript disabled.
- **Repository metadata.** A build-time script reads a few fields from the GitHub API for an allowlist of repositories and writes a snapshot. If the API fails or returns something malformed, the committed snapshot is kept. New repositories are reported for review and never published automatically.
- **Delivery.** GitHub Actions lints, type-checks, runs unit and end-to-end tests, builds and deploys. A failing step stops the deployment. A weekly scheduled run refreshes the metadata.

## Engineering decisions

### No UI framework

The interactive parts are five demos and three small controls. A component framework would have added a runtime to every page for the benefit of a few. Custom elements over server-rendered markup keep the home page at {m.homeJsGzipKb} kB of compressed JavaScript and make "works without JavaScript" a property of the architecture, not a fallback to maintain.

The cost is more manual DOM code in the demos, and no shared state library. For this size that is a fair trade.

### Native platform features first

The command palette is a `<dialog>`: the browser supplies the focus trap, Escape handling, the inert background and focus restoration. The mobile menu is a `<details>` element. Page transitions are cross-document view transitions declared in CSS, which simply do nothing in browsers that lack them. None of these needs a client-side router.

### Content rules as tests

A unit test reads every case study and fails if a required section is missing, if a team project lacks named collaborators or its role line, if a scrollable table cannot be reached by keyboard, or if the text contains phrasing the site must not use — an employment claim for a hackathon sponsor, a safety-certification claim, a description of rule-based work as machine learning. It is a narrow net, but it catches the mistakes that matter most on a page about oneself.

### Demos are re-implementations, tested against the originals

Each demo's logic is a pure TypeScript module. The audits exported fixtures from the original projects — monitor verdicts across threshold sweeps, KPI values, aggregation totals — and the unit tests assert that the port reproduces them. The demo bar on each page states what the demo is: synthetic data, a static snapshot, or a simulator re-run.

## Limitations

- WebKit was tested through Playwright's WebKit build, which is not Safari itself; a manual check in Safari is still open.
- No real-device or screen-reader testing yet; phone and tablet results come from emulation.
- CV downloads appear only once the documents are approved; until then the recruiter brief offers a request by email.
- The content tests check wording patterns, not truth. Accuracy still depends on the audits and on review.
- English only.
